# Arvexo Radar: цели продукта

**Версия:** v0.1.0 — Hackathon MVP
**Статус:** продуктовая спецификация

## 1. Назначение

Цели переводят [Vision](./01-vision.md) и [бизнес-проблему](./02-business-problem.md) в проверяемые результаты. Числовые показатели качества моделей не выдумываются: пороги утверждаются после получения размеченной выборки и baseline.

## 2. Главный результат

После загрузки поддерживаемого dataset CTO и AI Platform Owner получают воспроизводимую, объяснимую и безопасно подготовленную картину использования корпоративного AI и обоснованные следующие действия.

## 3. Цели Hackathon MVP

### G-01. Надёжный сквозной анализ

Система проводит dataset через Upload → Validation → Normalization → Sensitive Data Masking → Embeddings → Classification → Scenario Clustering → Scenario Naming and Summarization → Business Insights → Executive Dashboard → PDF Report.

**Проверка:** каждый этап имеет статус; принятые записи завершаются результатом либо явной ошибкой; повторный запуск на тех же данных и конфигурации воспроизводим в пределах недетерминированной генерации, provenance которой сохранён.

### G-02. Понятная структура использования

Показать распределение запросов по бизнес-категориям и обнаруженным use cases, включая количество, долю, confidence/quality и маскированные representative samples.

**Проверка:** сумма и знаменатели агрегатов объяснимы; неизвестные случаи не скрываются и попадают в `Other/Unknown` или noise.

### G-03. Проверяемые управленческие выводы

Сформировать бизнес-инсайты и рекомендации, связанные с конкретными наблюдениями.

**Проверка:** каждый вывод содержит evidence references, тип (`observation`, `hypothesis`, `recommendation`) и ограничения; при отсутствии основания вывод не создаётся.

### G-04. Диагностика качества запросов и рисков

Показать prompt health и потенциальные sensitive-data/security findings без раскрытия найденных значений.

**Проверка:** findings агрегированы и прослеживаются до маскированных записей; секреты не появляются в UI, отчёте и логах.

### G-05. Польза для CTO

Executive Overview отвечает на «что происходит?» и «что делать дальше?», отделяя использование от доказанного экономического эффекта.

**Проверка:** demo script проходит без обращения к исходным немаскированным данным; top-сценарии, top-проблемы и действия видны на первом уровне.

### G-06. Устойчивость без внешней LLM

Локальная аналитика не зависит от доступности генеративного API. Доступны API provider, mock provider и подключаемый локальный provider для тестирования; H100 в v0.1.0 не используется.

**Проверка:** при недоступности API категории, кластеры и количественная аналитика сохраняются, а генеративные поля получают явный degraded status или безопасный fallback.

### G-07. Обработка длинных запросов

Pipeline проектируется с учётом среднего размера запроса `100k токенов` по ТЗ КРОК.

**Проверка:** длинный текст не передаётся целиком в embedding-модель или внешнюю LLM без контролируемой стратегии chunking, редукции и лимитов.

## 4. Критерии качества решения из ТЗ КРОК

| Критерий | Продуктовая интерпретация | Метод проверки |
|---|---|---|
| Понятность для CTO | Ясный overview и следующие действия | Прохождение demo script по ключевым вопросам |
| Качество группировки | Похожие запросы вместе, разные разделены | Экспертная выборочная оценка и cluster metrics |
| Интерпретируемость | Понятные названия и примеры | Проверка samples, explanations и confidence |
| Устойчивость | Контролируемые ошибки и degradation | Негативные и интеграционные тесты |
| Воспроизводимость | Сохранены версии, параметры и provenance | Повторный запуск фиксированной конфигурации |
| Скорость | Progress и отсутствие неограниченных операций | Замеры на согласованном reference dataset |
| Продуктовость | Аналитика приводит к проверяемому действию | Связь insight → evidence → recommendation |

## 5. Метрики без фиктивных целей

До появления baseline система должна собирать:

- долю валидных, отклонённых и обработанных записей;
- долю `Other/Unknown` и noise;
- распределение classification confidence и cluster quality;
- количество и типы prompt-health/security findings;
- длительность этапов и число retry/cache hit;
- долю генеративных результатов в статусах generated, cached, fallback и failed;
- долю insights с полным evidence trail.

Целевые пороги утверждаются после проверки dataset и не должны подбираться только под демонстрационную выборку.

## 6. Ограничение понятия эффективности

Логи запросов подтверждают использование, намерения, повторяемость, качество формулировок и потенциальные точки автоматизации. Для доказательства экономии времени, качества результата или ROI нужны outcome-данные. До их появления Radar показывает proxy signals и явно маркирует их как такие.

## 7. Критерии готовности MVP

MVP готов к демонстрации, если реализованы все P0-требования из [Functional Requirements](./07-functional-requirements.md), основной flow воспроизводим локально, mock mode не требует внешнего ключа, а PDF и dashboard используют один набор рассчитанных показателей.
